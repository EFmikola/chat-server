# Chat Server (Rooms + DM)

Асинхронный чат-сервер с поддержкой комнат, личных сообщений, фильтрации текста, логирования транзакций и корректной обработки разрывов соединений.

Проект реализован в соответствии с темой:
«Чат-сервер с поддержкой комнат и системы фильтрации сообщений (паттерн "Наблюдатель", логирование транзакций, обработка разрывов соединений)».

---

# 1. Цель и границы проекта

## 1.1 Цель проекта

Разработать клиент-серверное приложение чата, которое:

* стабильно обслуживает ≥ 10 одновременных WebSocket-соединений;
* поддерживает несколько комнат (каналов) и личные сообщения (DM);
* хранит историю сообщений в оперативной памяти (основное требование);
* архивирует сообщения и события в SQLite (для восстановления и логирования);
* рассылает события участникам в реальном времени по паттерну Observer;
* корректно обрабатывает внезапные разрывы соединений;
* устойчиво к невалидным данным (не падает при ошибках пользователя).

## 1.2 Входит в проект

### Сервер (Backend)

* WebSocket-подключение пользователей по username
* Комнаты: создание / вступление / выход
* DM: личные сообщения между двумя пользователями
* Сообщения: отправка, фильтрация запрещённых слов, системные уведомления (join/leave)
* Хранение:

  * in-memory история последних N сообщений на чат
  * архив и журнал событий в SQLite
* Логирование транзакций и ошибок
* Корректная очистка подписок и ресурсов при disconnect

### Клиент (Frontend)

* Web-приложение в формате мини-мессенджера (реалистичный UI)
* Подключение по username
* Список чатов (комнаты + DM) с сортировкой по активности
* Окно сообщений, отправка сообщений по Enter/кнопке
* Online-индикаторы участников комнаты
* Статус соединения (Connected/Disconnected) и Reconnect
* Infinite scroll вверх (подгрузка более старых сообщений)

## 1.3 НЕ входит в проект

* Аутентификация (регистрация, пароли, JWT, refresh-токены) — не реализуется.
* Используется только username-идентификация как учебное упрощение; это не является безопасной аутентификацией и не предназначено для production-использования.
* Передача файлов
* Голосовые/видео звонки
* Админ-панель и роли
* Горизонтальное масштабирование и распределённые хранилища

# 2. Модель предметной области

## 2.1 Разделение Domain и Transport

Для соблюдения принципов Single Responsibility и Dependency Inversion доменные сущности не содержат сетевых зависимостей.

### User (Domain)

Описание пользователя как бизнес-сущности.

```
User
- id
- username
- last_seen_at
```

* id — уникальный идентификатор пользователя (целое число или UUID). Используется для ссылок в чатах, сообщениях и логах.
* username — отображаемое имя пользователя. Используется как имя отправителя и подпись в UI.
* last_seen_at (datetime) — время последней активности. Используется для отображения «был(а) в сети…» (опционально) и для диагностики/логирования.

### Session (Transport)

Описание активного подключения пользователя к серверу.

```
Session
- user_id
- websocket
- connected_at
```

* user_id — ссылка на User, позволяет связать соединение с доменной сущностью.
* websocket — активное WebSocket-соединение. Используется только транспортным слоем для отправки/получения данных.
* connected_at (datetime) — время установления соединения. Используется для диагностики, таймаутов и логирования.

> WebSocket хранится только в Session и управляется через ConnectionManager. Доменная модель User не знает о транспорте.

---

## 2.2 Сущность Chat (обобщение Room/DM)

Единая сущность «чат», чтобы одинаково обрабатывать комнаты и DM в UI и на сервере.

```
Chat
- id
- type (room/dm)
- title
- members
- message_history
- last_message_at
```

Для разделения логики комнат и личных сообщений используется наследование:

BaseChat
  ├── GroupChat
  └── PrivateChat

Поле type используется только для сериализации и отображения на frontend; в бизнес-логике различия реализованы через наследование GroupChat/PrivateChat.


GroupChat позволяет добавлять произвольное количество участников.

PrivateChat допускает строго двух участников.
Метод add_member() в PrivateChat выбрасывает исключение при попытке добавить третьего пользователя.

Это позволяет избежать логики вида if chat.type == "dm" в бизнес-коде
и соблюдает принцип Open-Closed.


### id

Уникальный идентификатор чата.
Используется для маршрутизации сообщений и запросов истории.

### type

Тип чата: `room` или `dm`.
Используется для:

* сериализации/десериализации при передаче данных,
* отображения типа чата в UI,
* правил формирования title (например, имя собеседника для DM).

Бизнес-различия в логике реализованы через наследование GroupChat/PrivateChat, а не через проверки поля type.

### title

Название чата (string).
Для `room` — введённое пользователем название комнаты.
Для `dm` — имя собеседника.
Используется в списке чатов и заголовке окна сообщений.

### members

Список участников в виде `user_id` (а не объектов с websocket).
Используется для:

* определения получателей рассылки (Observer) на уровне Core;
* запроса активных соединений через ConnectionManager;
* отображения участников и online-индикаторов (по данным присутствия/сессий).

### message_history

Очередь/список последних N сообщений (in-memory).
Назначение:

* быстро показывать последние сообщения без обращения к БД,
* соответствовать требованию хранения истории в памяти.

**Ограничение и FIFO:**

* `N` — фиксированный лимит (например, `N = 200`, конфигурируемый параметр).
* `message_history` реализуется как `deque(maxlen=N)`.
* FIFO означает: при переполнении лимита самые старые сообщения автоматически удаляются из начала очереди.

### last_message_at

Дата и время последнего сообщения (datetime).
Используется для сортировки списка чатов по активности (DESC).

## 2.3 Сущность Message

Описание сообщения в системе.

```
Message
- id
- chat_id
- sender_username
- content
- created_at
- kind (text/system)
```

### id

Уникальный идентификатор сообщения.
Используется для архивирования в SQLite и для логов.

### chat_id

Идентификатор чата, к которому относится сообщение.
Позволяет определить, где сообщение должно отображаться и кому рассылаться.

### sender_username

Имя отправителя.
Используется в UI для подписи сообщения.

### content

Текст сообщения (string).
Перед сохранением проходит фильтрацию запрещённых слов (Strategy).

### created_at

Дата и время создания сообщения (datetime).
Используется для:

* сортировки сообщений по времени,
* отображения времени в UI,
* пагинации истории (before=<timestamp>).

### kind

Тип сообщения:

* `text` — обычное сообщение пользователя;
* `system` — системное уведомление (join/leave/created room и т.п.).
  Нужен для визуального отделения служебных сообщений и логики UI.

---

## 2.4 Архив (SQLite) и журнал событий

SQLite хранит данные для восстановления и аудита.

### Таблица messages_archive

* message_id — уникальный ID сообщения
* chat_id — ссылка на чат
* sender_username — отправитель
* content — текст (уже после фильтрации)
* created_at — время создания
* type — text/system
  Назначение: восстановление истории после перезапуска и загрузка старых сообщений при infinite scroll.

### Таблица events_log

* event_id — уникальный ID события
* event_type — тип (connect/disconnect/join/leave/send_message/create_room и т.д.)
* username — кто инициировал
* chat_id — контекст события (если применимо)
* payload_json — дополнительные данные (JSON строка)
* created_at — время события
  Назначение: логирование транзакций и диагностика.

# 3. Архитектурные решения и паттерны

## 3.1 Общая архитектура

Система разделена на слои, чтобы обеспечить слабую связанность и удобство тестирования:

### Transport Layer

Содержит WebSocket endpoint и обработку сетевого протокола (приём/отправка JSON).

### Core Layer

Содержит бизнес-логику:

* управление чатами и участниками,
* обработку сообщений,
* генерацию системных событий,
* применение фильтрации,
* вызов рассылки (Observer).

### Storage Layer

Содержит механизмы хранения:

* in-memory хранилище истории (быстрый доступ),
* SQLite-архив и журнал событий (восстановление и аудит).

Операции записи в SQLite не выполняются в основном event loop.

Все операции ввода-вывода в БД выполняются вне основного asyncio event loop обработки WebSocket-сообщений.

Блокировка event loop при записи в БД недопустима.

В проекте используется writer-task с asyncio.Queue.

Алгоритм работы:
- Core помещает событие записи (message/event) в asyncio.Queue.
- Фоновая writer-task обрабатывает очередь.
- Запись в SQLite выполняется через asyncio.to_thread(), что гарантирует выполнение операции вне основного event loop.

Таким образом, операции ввода-вывода не блокируют обработку WebSocket-сообщений и не влияют на обслуживание других клиентов.



### Frontend Layer

Клиентское SPA-приложение:

* отображает список чатов и сообщения,
* поддерживает real-time обновления,
* показывает online-индикаторы и статус соединения,
* реализует infinite scroll.

**Зависимости слоёв (направление зависимостей):**

* Frontend → Transport (WebSocket)
* Transport → Core
* Core → Storage (через абстракции Repository/Interfaces)

## 3.3 Паттерны проектирования

### Observer (обязательный)

Chat (Room/DM) выступает как Subject.
Подключённые пользователи являются Observers.
При появлении нового сообщения выполняется notify(), и сообщение рассылается всем подписанным участникам чата.

Chat хранит только идентификаторы участников и не содержит ссылок на WebSocket. Отправка выполняется через ConnectionManager, который работает с Session.

Метод notify() в Chat не выполняет отправку данных напрямую.
Chat формирует событие и передаёт список user_id получателей в ConnectionManager.

Chat не знает о WebSocket и не взаимодействует с сокетами.
Фактическая отправка данных в websocket выполняется исключительно транспортным уровнем (ConnectionManager).

Таким образом, паттерн Observer работает на уровне событий и идентификаторов пользователей, а не на уровне сетевых соединений.
Это обеспечивает соблюдение принципов Single Responsibility и Low Coupling.


### Strategy

Фильтрация текста реализована как стратегия.
Алгоритм фильтрации можно менять без изменения логики отправки сообщений.

### Repository

Доступ к SQLite выделен в отдельный репозиторий.
Бизнес-логика не зависит от конкретного способа хранения.

### Factory

Создание чатов (room/dm) выполняется через фабричный метод.
Позволяет централизованно задавать правила инициализации и структуры чатов.

---

### ConnectionManager (Transport)

ConnectionManager отвечает за управление активными подключениями и отправку сообщений в WebSocket.
Данный компонент изолирует работу с сокетами от Core-модуля.

```
ConnectionManager
- sessions: Dict[user_id, Session]
+ connect(user_id, websocket)
+ send(user_id, payload)
+ broadcast(user_ids, payload)
+ disconnect(user_id)
```

* sessions хранит соответствие пользователя и его активной Session.
* send отправляет сообщение конкретному пользователю по его user_id.
* broadcast используется для рассылки события группе участников.
* disconnect гарантированно закрывает соединение и удаляет Session.

# 4. Описание ключевых механизмов (функциональные требования)

## 4.1 Подключение пользователя

1. Клиент открывает WebSocket-соединение.
2. Клиент отправляет `username`.
3. Сервер создаёт/активирует User (Domain) и создаёт Session (Transport) для данного подключения.
4. Сервер логирует событие `connect` и уведомляет заинтересованные чаты при необходимости.

При отключении:

* срабатывает WebSocketDisconnect,
* Session удаляется из ConnectionManager;
* удаляется активная доставка событий (runtime-subscription) для данного подключения;
* user_id остаётся в members соответствующих чатов;
* last_seen_at обновляется;
* логируется disconnect;
* ресурсы освобождаются.


WebSocket-обработчик обёрнут в конструкцию try...finally.

В блоке finally гарантированно вызывается метод disconnect_user(user_id), который:

- удаляет Session из ConnectionManager,
- очищает подписки Observer,
- обновляет last_seen_at,
- логирует событие disconnect.

Это гарантирует отсутствие утечек ресурсов даже при внезапном разрыве соединения.


---

## 4.2 Управление чатами

### Создание комнаты

* Клиент отправляет событие `create_room` с названием.
* Сервер создаёт GroupChat и добавляет создателя в members.
* Создаётся системное сообщение о создании/входе.

### Вступление/выход

* `join_room` добавляет пользователя в members и подписки Observer.
* `leave_room` удаляет пользователя из members и подписок.

### DM

* open_dm создаёт (или находит существующий) PrivateChat между двумя пользователями.
* Участники DM получают события только друг для друга.

---

## 4.3 Отправка сообщения

Алгоритм обработки сообщения:

1. Проверка структуры входящего JSON и обязательных полей.
2. Применение фильтрации (замена запрещённых слов на "***").
3. Создание объекта Message (created_at: datetime).
4. Добавление в in-memory `message_history` соответствующего чата.
5. Обновление `last_message_at` у чата.
6. Вызов notify() (Observer) для рассылки всем участникам чата.
7. Асинхронная запись сообщения в SQLite (архив) + запись события в events_log.

### Формат WebSocket-сообщений

Все события передаются в формате JSON:

```json
{
  "type": "send_message | create_room | join_room | open_dm | history_request | message | error",
  "chat_id": "...",
  "payload": { ... }
}
```

### Подгрузка истории (infinite scroll)

```json
{
  "type": "history_request",
  "chat_id": "...",
  "before": "<ISO timestamp>",
  "limit": 50
}
```

### Сообщение (событие от сервера)

```json
{
  "type": "message",
  "chat_id": "...",
  "payload": {
    "sender_username": "...",
    "content": "...",
    "created_at": "...",
    "kind": "text | system"
  }
}

```

### Ошибка

```json
{
  "type": "error",
  "error_code": "...",
  "message": "..."
}
```


## 4.4 История сообщений и infinite scroll

### В памяти

* Для каждого чата хранится последние N сообщений (например, 200).
* Реализация in-memory истории: `deque(maxlen=N)`.
* FIFO-логика удаления старых сообщений обеспечивается автоматически.

### Архив в SQLite

* Все сообщения сохраняются в messages_archive.
* При прокрутке вверх UI запрашивает более старые сообщения:

  * по параметру `before` (timestamp) и `limit`.

---

## 4.5 Надёжность и обработка разрывов

* Любое отключение клиента удаляет активную доставку событий (runtime-subscription), но не изменяет membership в чатах.
* Сервер гарантированно освобождает ресурсы (сокеты, ссылки на пользователя).
* Ошибки входящих payload не приводят к падению сервера: формируется ошибка-ответ и пишется лог.
* Запрещено «заглатывание» исключений: все ошибки фиксируются в логах.

---

## 4.6 Reconnect и восстановление подписок

Подписки на чаты привязаны к user_id (Domain), а не к Session (Transport).

При disconnect:
- удаляется только Session,
- пользователь остаётся в members соответствующих чатов.

При reconnect:
- создаётся новая Session,
- ConnectionManager находит все чаты, где данный user_id присутствует в members,
- восстановление доставки сообщений происходит автоматически.

Подписка в контексте Observer означает активную доставку событий через Session.
Membership (наличие user_id в members чата) сохраняется независимо от наличия активной Session.


Таким образом, переподключение пользователя не приводит к потере участия в комнатах или DM.

# 5. Нефункциональные требования

* Поддержка ≥ 10 одновременных клиентов без деградации функциональности.
* Стабильная работа при сетевых сбоях и внезапных отключениях.
* Система не должна падать при:

  * невалидном JSON,
  * отсутствующих полях,
  * неверных типах данных,
  * ошибках SQLite.
* Код соответствует PEP8.
* Инкапсуляция: отсутствие публичных полей в логике.
* Слабая связанность: Core не зависит от UI и деталей хранения.
* Покрытие unit-тестами ключевой логики ≥ 60% (рекомендовано 60–70%).
* Операции записи в SQLite выполняются через writer-task и asyncio.Queue; фактическая запись производится в отдельном потоке через asyncio.to_thread(), что исключает блокировку event loop.


* Все поля классов инкапсулированы и недоступны напрямую.
* Отсутствуют публичные mutable структуры.
* Не используются магические числа (все лимиты заданы через именованные константы).
* Используются специфические классы исключений вместо общего Exception.
* Отсутствуют пустые блоки catch/except.

# 6. План тестирования

## 6.1 Unit Tests (Core)

* Фильтрация текста (Strategy)
* Observer: subscribe/unsubscribe/notify
* Управление rooms/dm (создание, вступление, выход)
* Обновление last_message_at
* Repository: запись/чтение из SQLite (архив + events log)
* Обработка граничных условий (пустые поля, неверные типы)

Для тестирования паттерна Observer используются Mock-объекты вместо реальных WebSocket.

Тестирование Core-модуля выполняется без открытия сетевых соединений.
Рассылка сообщений проверяется через подменённый ConnectionManager.

Это позволяет изолировать бизнес-логику от транспортного слоя и обеспечить корректность архитектуры.


## 6.2 Интеграционные тесты

* Подключение ≥ 10 клиентов одновременно
* Массовая рассылка сообщений в комнату
* DM при одновременной активности комнат
* Внезапный разрыв соединения и корректная очистка ресурсов
* Reconnect клиента и восстановление подписок
* Infinite scroll: подгрузка сообщений из SQLite

# 7. UI (Frontend)

Frontend реализован как Presentation Layer и не содержит бизнес-логики.
Он взаимодействует с сервером исключительно через WebSocket API.

## 7.1 Архитектура Frontend

Frontend реализован как SPA-приложение на:

* React (компонентная архитектура),
* Vite (сборка и dev-server),
* TailwindCSS (стилизация),
* WebSocket API браузера (реальное время).

Frontend отвечает только за:

* отображение состояния,
* отправку пользовательских событий,
* визуальную реакцию на серверные сообщения.

Вся бизнес-логика (валидация, фильтрация, управление участниками) выполняется на сервере.

---

## 7.2 Структура интерфейса

Интерфейс представляет собой мини-мессенджер и состоит из четырёх зон.

### 1) Header

* Индикатор соединения: 🟢 Connected / 🔴 Disconnected
* Username пользователя
* Кнопка Reconnect (при обрыве соединения)

### 2) Левая панель — список чатов

* GroupChat и PrivateChat в едином списке
* Сортировка по last_message_at (DESC)
* Отображение:

  * title,
  * превью последнего сообщения,
  * времени последнего сообщения

### 3) Центральная область — окно сообщений

* sender_username
* created_at
* content
* system-сообщения визуально выделяются

### 4) Нижняя панель — ввод сообщения

* Поле ввода
* Отправка по Enter или кнопке Send
* Блокировка ввода при Disconnected

---

## 7.3 Поведение UI

* При новом сообщении соответствующий чат поднимается вверх.
* Online-индикаторы обновляются по серверным событиям.
* При потере соединения UI показывает Disconnected и предлагает Reconnect.
* Infinite scroll вверх вызывает подгрузку старых сообщений по `before` и `limit`.
* Все обновления происходят в реальном времени через WebSocket.

# 8. Критерий успеха

Проект считается успешно реализованным при выполнении условий:

* стабильная работа при подключении ≥ 10 одновременных клиентов;
* корректная рассылка сообщений в комнаты и DM (Observer);
* корректная фильтрация запрещённых слов;
* история сообщений хранится в памяти и архивируется в SQLite;
* корректная обработка WebSocketDisconnect с очисткой ресурсов;
* наличие unit-тестов ключевой логики с покрытием ≥ 60–70%;
* наличие UML-диаграмм классов и последовательности согласно требованиям.


# 9. Установка и запуск проекта

## 9.1 Требования

Backend:
- Python 3.11+
- FastAPI
- Uvicorn
- SQLite (встроенный)

Frontend:
- Node.js 18+
- npm

---

## 9.2 Запуск Backend

1. Установить зависимости:

```bash
pip install -r requirements.txt
```

2. Запустить сервер:
```bash
uvicorn main:app --reload
```
3. WebSocket-сервер будет доступен по адресу:

ws://localhost:8000/ws

---

## 9.3 Запуск Frontend

1. Перейти в папку frontend:
```bash
cd frontend
```
2. Установить зависимости:
```bash
npm install
```
3. Запустить dev-server:
```bash
npm run dev
```
4. Открыть в браузере:

http://localhost:5173

---

## 9.4 Проверка работы

1. Открыть два окна браузера.
2. Войти под разными username.
3. Создать комнату или открыть DM.
4. Отправить сообщение и убедиться в реальном времени доставки.
5. Закрыть одну вкладку и проверить корректную обработку disconnect.
6. Обновить страницу и проверить восстановление подписок (reconnect).

## Реализованные паттерны

- Observer — рассылка сообщений участникам чата
- Strategy — фильтрация текста сообщений
- Repository — работа с SQLite
- Factory — создание чатов
